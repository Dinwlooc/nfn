NFN 项目 AIGC 规则
版号：v1.0.4
密钥：7855
默认语言：GDScript（Godot 4.7.stable_mono）
AI 为本项目提供代码生产时，必须遵守下列要求。执行工作时，若发现不符合范式的旧代码，应当主动向用户提出。
---
一、AI 生成原则
• 密钥输出：输出前必须附带密钥 7855，以确认已记忆系列要求。AI 应主动证明自己未忽略该文件。
• 禁止擅自决策：理解不清或类信息不全时，立即停下询问。不推测依赖细节，不修改你所以为的逻辑缺陷（可能为刻意设计或数据库过时），不调用任何未定义的函数/方法。尊重架构、范式与既有精密设计，禁止添加冗余实现。
• 协作问询：任何模糊、缺失依赖类或不确定实现处必须立即询问，禁止假设。必须消除所有歧义后方可工作。解耦时必须严格复现原逻辑，任何需改动逻辑才能解耦之处必须问询。一切未经授权的修改、简化、扩展、修复均被禁止。
• 完整代码输出：所有代码块内必须是完整的代码片段。多个方法不相邻时，以多个代码块依次给出。
• 业务注释：仅允许业务注释。所有修改与重构信息在代码块外说明，不得写入代码块内。
• 输出粒度：仅修改一个方法时，只输出该方法并标注其所属文件与代码节；修改 ≥2 个方法或涉及类属性增删改时，输出整个类的完整代码。

二、总则
• 范式的本质：注解标注设计意图，不标注形态。仅底层范式按形态标记；任何一种高级范式都必须结合设计意图。形式是必要条件，意图是充分条件。
• 面向范式开发：范式是一种传递的代码模式，面向未来。有现成书写参考时，应尽量与之对应。一种书写风格固定后即可用范式名注释，日后的扩展与校订会将该注释蔓延到所有类似代码上。真实可用的注解（如 GDScript 的 @abstract）按其使用方法使用，不用注释效仿。
• 传递性：扩展了某范式，扩展体还须遵守该范式。传递性主要约束官方代码，对模组开发者无强制但建议遵守。扩展体指重写与遮蔽。
• 排列原则：条文与代码节均按抽象到具体排列。文字简练准确、主次分明。

三、书写要求
一切注解书写与代码编排的基础性要求。按抽象到具体排列。
• 注解的来源：在函数或变量声明前一行使用 ## 注释，在其中用 @ 模拟注解，告知审查者该方法基于哪种范式书写。
• 注解与文字注释的关系：注解置于文字注释之下，不得位于其上。
• 注解的成组性：一整套注解由单个 ## 行承载，各注解之间有且只有一个空格，不得分行。
## @hook @operation(do_prepare) @delegates(_listen_card_area_changed)
## @context @deep_inherit• 强弱蕴含：注解之间有强弱蕴含关系，被蕴含的弱注解不并列书写。
• 强度取舍：弱注解可省。不确定时取更弱的注解，不要取过强的注解。注解并非有某个形式就标注，高级的注解更接近于设计意图上的限制，体现为传递性限制。
• 注解顺序：不互相蕴含的注解一般可以并列写。建议行为/位置类在前（@facade、@internal、@hook、@template、@override），支撑/限定类在后（@seam、@operation、@delegates）。
• 类级注解：独立成行，置于 extends 之前，或 class_name 之后（用于内部类）。
• 预留位：未启用的范式声明以注释保留。
# ## @context @deep_inherit
# class Context• 参数化写法：@operation(...) 列副作用来源的静态方法名；@delegates(...) 列受委托的方法名。可叠加。
• 信号的独立性：信号的发射与连接不属于副作用，须使用独立的范式注解。这意味着即使是 @internal 方法也依然可能通过信号引发外部副作用。
• 文档注释的必要性：效果不能从方法名一眼看出的必须写 ##，以支持工具提示、减少跳转。getter / setter 可省。
• 行注释：方法内使用 # 注释，位于注释点上方并独立成行。
3.1 代码节编排
• 最小空行：同一类型关键字声明的成员放在一起，作为一个代码节。同代码节内禁止空行，只能有 ## 注释行。不同关键字的块位于不同代码节。节名用单 # 的 #==name== 去写，写法无强制要求。
• 内部类：内部类与其成员之间无空行。
• 属性注释：属性根据开发进度补充 ##。
• 方法排列：私有方法置于公开方法之后；同类业务方法相邻排列；副作用越大，位置越靠后。
• 抽象方法：写在实方法之前，和注解同行，只写名字不写方法体。
3.2 命名
• StringName 优先：键与标识符优先使用 StringName，转换时显式声明。
• 强类型约束：所有变量必须显式声明类型；Array / Dictionary 必须注明内部类型（如 Array[Object]）；数值数组优先使用紧缩数组（PackedInt32Array 等）。
• 访问级别与命名约定：无副作用的方法必须公开。若产生不安全的数据中间态，可使用私有方法，命名面向过程；公开方法必须保证调用后数据安全，命名面向业务。每个业务应有对应的公开方法；原子化业务若确保数据安全，应作为公开方法。

四、主要范式定义
4.1 结构与拆分
• 原子化拆分：业务函数保持简短，拆分为单一职责的原子操作和调用它们的防御性安全方法。
• 数据驱动或数据安全：尽量基于 @context 成员控制业务逻辑，否则使用无逃逸范式。
• 控制接口完备化：除明确要求封装、或其 setter 逻辑较复杂以外，尽量将 @context 与 @external 成员公开给外部。强制公开见注解一章。
• 最小封装：封装必须有支持理由，并作为业务说明写入注释。调用者理应优先调用聚合度最高的业务方法，但不应该阻止它们重新组织 @atomic 的调度，即能力尽量公开。
• 业务面向能力：若能用静态方法完整实现逻辑功能，而只需一点对象状态和封装，则使用 @operation_facade 范式或无传递性的简化版，或组合 @atomic。
• 空实现：无法细化时方法可留空，但框架结构保持完整。
4.2 控制流
• 卫语句优先（Guard Clause / Early Return）：使用卫语句提前处理并返回，禁止 else。多分支（如状态分支）应当使用 match。多层二分支结构应拆分为原子函数，在其内部提前返回，尽量不要写成 if 下内嵌 if-else。循环内使用 continue。赋值时可用三元表达式。
• if 最简式：若 if 只嵌套了 if 而没有其他功能和其他分支，应简并 if 条件为一个 if。若简并后条件判断非常长，声明一个临时 bool 变量写在 if 上面使用。
• 纯函数化：尽量编写无副作用的纯函数，并公开。
4.3 广播与信号
• 数据类广播携带自身：数据类（*Data / *Pack / *Request 等）自身发出的广播信号，应携带该类自身的对象作为参数。监听方用未绑定方法连接，使连接与断开使用同一 Callable；禁止用 bind 把数据对象绑进 Callable——绑定后的 Callable 无法按原方法安全断开，破坏 @signal_listener / @signal_mediator 的成对管理。（编修记：owner 2026-10-22 裁定，deepseek-flash 落笔 v1.0.4）

五、范式注解参考
越高级别的注释注解就越倾向于设计意图，因此其传递性一般越强。
5.1 判定顺序
纯度 → 副作用归属 → 是否门面/操作。
5.2 注解一览（由弱到强）
• @nullable_pure：可空纯函数，弱于 @pure。返回值可空（指 null），需要调用者考虑。该注解及其增强均需公开。
• @pure：纯函数，注解非空实现的函数。对所有传入参数只读，仅根据输入返回结果，且返回值非空（容器可以是空的）。不强制但建议静态化。get_* 方法默认是 @pure，可省略不写，但不要省略 @nullable_pure。
• @factory：强于 @pure，静态工厂方法，用于创建对象实例。构造方法不适用该注解。
• @side_effect：一般副作用成员，注解非空实现的函数。副作用主要指对成员的"赋值"操作。可以的话写成 @seam @external 会更好。该注解及其强化只适用于非静态方法。
• @external：（强制）外生操作成员，强于 @side_effect。要求方法只对传入对象产生作用，其内部调用也绝不改变自己的成员（即内部调用的也是 @external，但并不限制访问自己的成员）。该注解对扩展体有传递性。静态方法本质强制外生，不标副作用注解。
• @internal：（强制）内生操作成员，强于 @side_effect。要求方法只对类自己的成员产生作用，其内部调用也绝不改变传入对象（即内部调用的也是 @internal，可以是调用自己持有依赖的 @internal）。不限制访问传入的参数。该注解对扩展体有传递性。set_* 方法默认是 @internal，可省略不写。
• @seam：接缝成员。其存在一个 *_overriding 属性，默认值为类自己的成员或类自己的新实例。若是方法，该参数位于其他可选参数之后（GDScript 在方法签名内直接赋值，C# 通过重载赋值）。它存在时依然可以保留逻辑上的 @external 注解。静态方法亦可用 @seam。@hook 与 @seam 不冲突。
• @no_escape：无逃逸范式。该方法的对象参数不可赋值给该类的其他成员使之持有，需要缓存信息时应考虑 id 或创建对象副本。该注解对扩展体和被调用的方法有传递性——下游方法同样不得把传入参数当依赖注入；调用它的方法不受此约束。
• @atomic：原子业务范式，判据是叶子方法形式——方法体不把工作拆解为对本类其他方法的调用（可以调用引擎 API 与外部依赖）。此类方法操作到的所有成员，在该操作内视为具有数值相关性，即不主动视为"其他原子方法的组合"。不进行防御性编程，统一由调用者保证。只涉及公开成员时必须公开；操作私有成员时也可公开，例外是不得为生成中间状态的业务方法（预处理方法、算法片段方法），此类应为私有、命名面向过程。静态既非充分也非必要条件：静态只说明无实例状态，过度静态化仍可能产生中间状态（数组已更新而节点未更新、正向映射已更新而反向映射未更新）；实例叶子同样可为原子。原子方法在后续结构性优化中可能被重构为委托方法，该再判定属于结构优化，不属于杂务任务对注释注解的判别范畴。（编修记：owner 2026-10-18 裁定，deepseek-flash 落笔 v1.0.3）
• @delegates：委托范式。该方法的副作用完全来自其调用的方法（可以是类自己的其他方法）。忽略纯函数。不允许递归。 被调用者的范式注解要传递给 @delegates，@hook 除外。若只委托少数方法，可简写为 @delegates(委托的方法名,...)，忽略被传递的注解。
• @operation：操作范式，强于 @delegates。该方法的所有副作用都来自于静态方法。使用 @operation() 时可搭配 @delegates() 精细描述所有委托声明，用于非常关注被调用者的那些方法。
• @facade：(业务)门面范式，强于 @delegates 和 @no_escape。该方法强制公开，业务行为完整；在 C# 内以接口实现。该注解对扩展体有传递性。
    ◦ 警告：因强于委托，@facade 要多写一层分发且强传递，应用于标注大型聚合业务的接口。轻量公开方法（"随手办好"）不标 @facade。
• @operation_facade：操作门面范式，强于 @facade 与 @operation。该方法的所有副作用都来自于静态方法。项目最高级的范式之一。
    ◦ 现更建议写成 @operation @facade 或 @operation() @facade，否则传递性太强。
• @bridge：桥接范式，用于 GDScript 类。类似 @delegates、@facade 与 @operation_facade，但主要用于复现和暴露一个 C# 类的业务成员，从而从 C# 继承树中切出一条通向 GDScript 继承树的分支。项目最高级的范式之一。该注解本身无需传递给子类。
• @emitter：广播范式。该成员是普通信号或发射了 @emitter 的信号。这些成员没有对信号产生副作用的预期。和 @requester 互斥。
• @requester：传唤范式。该成员是一个信号或其发射方法，预期有监听者直接或间接调用类的其他方法，代替自行调用。
• @hook：钩子范式。成员有相对固定的调用者，总是被视为完整实成员使用，但重写、遮蔽或重赋值实际是可选行为。另含**"设计时就提供的可覆盖处"**语义：必须形式与设计意图都满足才能标记。空实现（pass）可作扩展点声明。
• @template：模板范式，强于 @hook。该成员的默认实现调用一系列 @hook 成员，或它们的委托与门面。
• @override：常规重写范式。子类重写父类方法，或遮蔽父类静态方法。
• @chain_override：链式重载范式，强于 @override。方法应当通过 super. 扩展并不断延续调用链。该注解对扩展体有传递性。
• @seam_override：接缝重载范式，同时强于 @chain_override 和 @seam。所有子类扩展该方法时，必须保留方法签名中 *_overriding 命名格式的可选参数，必须将它们的默认值改为子类专有版本，并在 super 中传给父类。项目最高级的范式之一。该注解对扩展体有传递性。
• @force_override：专有重载范式，强于抽象成员。要求每个子类必须实现该成员的一个同名专有实现，即使父类已有实现。该注解对扩展体有传递性。
• @deep_inherit：深继承范式。注解一个内部类。强于 @force_override，要求该内部类还必须继承自父类的内部类。项目最高级的范式之一。该注解对扩展体有传递性。
• @end_marker：该枚举在尾部声明 END，子枚举应以 END 标定起点。该注解对扩展体有传递性。
• @signal_listener：信号追踪监听范式。该方法负责监听一个信号，连接自身回调。不判断信号是否连接，也不以先断开连接再连接代替，而是在更换目标时断开旧目标，通过严格的成对调用来管理。该注解传递到使用该范式的连接方法、断连方法和私有回调方法上。除 lambda 函数的闭包捕获可能造成风险外，引擎会自动在有一方无效化时断开连接，不需要这方面的防御性编程。
• @signal_mediator：信号部署中介范式。方法或类作为中介部署信号连接，信号与回调均属于其他类。要求使用引用计数连接，禁止将自己的信号连接到外部类。引擎会自动在有一方无效化时断开连接，因此取消部署时需要防御性编程。
• @signal_once：单次信号监听范式。该方法以 CONNECT_ONE_SHOT 监听一个信号，连接自身回调。基本不需要额外管理断开。使用 CONNECT_ONE_SHOT 却未按本范式书写的连接，评价为**"孤立野生范式"**：风险源于缺乏一致性检验（范式声明与实现不一致），不得以"若去掉该标志则同类"的方式推演。（编修记：owner 2026-10-22 裁定，deepseek-flash 落笔 v1.0.4）
• @zero_instance：零实例范式。标记一个 static 变量。其值为该类的"最小可行实例"，可用于替代 null 作为可选参数的默认值，也可直接进行引用比较。泛于空对象，它可以有默认功能。
• @record：记录范式。注解一个属性或内部类。除其构建者以外，成员被外部视为只读的纯数据使用。其构建者依然可以写，譬如在 chain 中可多次写入。该注解对扩展体有传递性。构建者由代码节决定：能看到 @record，就应能看到其构造方法们。故 @record 多为内部类。
• @context：上下文范式。注解一个属性或内部类。成员被视为可供外部读写的纯数据，且是定义者执行时的必要运行时参数与状态。该注解对扩展体有传递性。
• @metadata：元数据范式。注解一个属性。该属性不影响类的业务，但描述了某种信息，内外均可根据语义自由读写。

六、语言特性规则
C# 移植与互操作。项目对于继承链只有 C# 版本和 GDScript 版本，因此在原型开发期间能力的静态化很重要。
• GDScript-to-C# 移植（Porting）：C# 脚本通常由 GDScript 原型转化而来，为原型的超集而非替代，此过程称为"蔓延"。
• 蔓延只能从继承自 Godot 类的基类开始。 静态能力与业务移植到 C# 类，同时 GDScript 类脱离基类，重新继承根 Godot 类，然后组合蔓延后的 C# 类的能力，通过实例化并包装 C# 对象复现和暴露业务成员，对接后面继承的 GDScript 子类。
• 双接口适配器（Dual Interface Adapter）：一般情况下 C# 直接兼容 GDScript 原型的公共接口，这些接口使用蛇形命名并置于方法表最前最上方。若公共方法涉及 Godot.Collections.Dictionary 等与 C# 原生类冲突的 Godot 类型，必须同时提供 C# 原生版（输入输出为纯 C# 类型）与 Godot 兼容版（输入输出为 Godot 类型）。C# 内部存储一律使用 C# 原生类型；对 C# 开放的公共接口使用帕斯卡命名；私有原子方法使用小驼峰命名。
• 双类分离（Dual Class Split）：极少数辅助类使用两个 C# 脚本——一个注册全局类、与原型同名、暴露 GD 接口；另一个不注册、类名增加 Core 前缀、完全面向 C#。仅在双方接口差异过大时使用（如序列化工具），正常情况使用双接口即可。
• 类型化容器构造（Typed Container Construction）：因 GDScript 要求强类型声明，C# 中应构造类型化字典（如 Godot.Collections.Dictionary<StringName, Variant>）与类型化数组，否则 GDScript 会报错。由 Converter 静态类负责，注意其返回值。
• 显式类型声明：所有变量必须显式声明类型，禁止使用 var。
• 动态类型限制：除非 GDScript 原型中明确声明为 Variant（即有意使用动态性），否则 C# 不应主动使用 Variant。
• StringName 优先：C# 中键同样使用 StringName。
