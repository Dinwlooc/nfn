# NFN 架构判读：覆盖矩阵、风险诊断与主张

keywords: 架构判读,覆盖矩阵,Martin,主序列,风险诊断

**摘要**：把 0009 的数字读成结论：现有指标在 12 个标准维度上覆盖 7 完整 + 3 部分（约 70%，原为 29%）；Martin 主序列指出 `System/Item` 是最脆弱层（被依赖 17.00 均、零抽象、D=0.66）；环依赖经追查来自类型声明而非业务调用——类型网 43%（2026-10-27 复跑口径），扣除类型标注、常量引用与签名参数后真实调用环仅剩两组；`RenderContext` 的 LCOM=349 与 `@delegates` 判定互相印证。

**数字时效**：本文数字取自 `0009` 的 2026-10-27 快照；LCOM / Ca / 传播成本已按同日复跑校准，**环的三口径里只有类型声明网是本轮实测**，调用网数字（19%、0%）来自更早有调用图工具的那次运行，重跑前不要引用为"当前值"。

## 一、覆盖矩阵：我们的指标量化了架构的多少

✓=可算且已实测；△=部分；✗=未覆盖

| 维度 | 状态 | 依据 |
|---|---|---|
| 复杂度（方法级） | ✓ | 原子度（分支/方法） |
| 复杂度（类级 WMC） | ✗ | 未做类内求和 |
| 封装 / 信息隐藏 | △ | 只有命名可见性，无"外部直接访问成员"计数 |
| 耦合（CBO / Ce / Ca） | ✓ | 0009 §四 |
| 内聚（LCOM） | ✓ | 0009 §4.3 |
| 继承（DIT） | ✓；NOC ✗ | 0009 §4.1 有 DIT，无子类数 |
| 抽象度（A） | ✓ | 0009 §4.1 |
| 稳定性相称（I、D） | ✓ | 0009 §4.1 |
| 传播成本（DSM） | ✓ | 0009 §四（0.3095） |
| 复用（QMOOD 式） | △ | 只数导出单元，未乘耦合惩罚 |
| 可测试性 / 可分析性（ISO 25010） | ✗ | 无测试套件数据 |
| 设计意图（范式台账） | ✓ | 0009 §二（标准框架无此维） |

**覆盖度：7 完整 + 3 部分 ≈ 70%**（口径初建时仅 2+3≈29%）。仍缺：WMC 类级、NOC、历史共变模块度、可测试性。

﻿## 一bis、该重点参考哪几个指标（v1.3）

按能不能指向决策排序：

| 优先 | 指标 | 阈值与读法 | 理由 |
|---|---|---|---|
| P0 | 调用网 SCC（真实环） | 大于 0 即评审；本轮未复跑，历史值 2 组 | 类型网的边多数只是签名，环化率是噪声 |
| P0 | Ca 热点（类级入耦合） | 大于 20 慎改；GameState 59、Player 54、Card 42 | 直接给出变更成本与测试重点 |
| P0 | 实体类的 A、I、D | D 大于 0.5 视为抽象配比失衡 | System/Item 实体 Ca 均 36（Card 42 / Player 54 / Item 12），A=0 → D 约 0.66；层均值 17.00 被数据类拉低 |
| P1 | LCOM（仅实体类、方法数不小于 5） | 大于 30 复核 | 转发器（RenderContext 349）是例外 |
| P1 | 层间调用方向 | 只看调用造成的双向 | 20 对双向里多数是信号与抽象方法签名 |
| P2 | 叶子率、注解台账、封装度 | 无阈值，看趋势 | 服务注释与范式治理，不作架构结论 |
| 不采用 | 类型网环化率、类型网传播成本 | — | 测的是 GDScript 强类型签名的可见性网 |

**判读纪律**：层均值必须标支配者（实体类 vs 数据类），否则 System/Item 会被误读成层内聚差——它其实是 3 个实体类加 3 个一两行方法的数据类。

## 二、7 项自创指标的定位（不夸大）

| 我们的指标 | 最近的已知度量 | 差异 |
|---|---|---|
| 封装度 | MOOD 的 EC／QMOOD 的 DAM | 只看命名可见性 |
| 安全性 | MOOD 的 DC（信息隐藏） | 由范式注解驱动，无标准对应 |
| 风险率 / 完整度 | 无标准对应 | **自创**，但有体分析支撑 |
| 复用密度 | QMOOD Reusability | 只数可导出叶子单元，不做耦合加权 |
| 原子度 | WMC（粒度不同） | 按方法计，WMC 按类求和 |
| 参数均 | CBO 的近似 | — |
| 叶子率 | **无标准对应** | 与 `@atomic` 的形式定义绑定 |

结论：**7 项中 2 项能对上标准度量，2 项自创但可解释，3 项属项目特有**。它们不能替代标准框架，只能补充"设计意图"这一标准框架缺的维度。

## 三、主序列诊断：三处结构性风险

D（主序列距离，0 最健康）在层级上的分布揭示了三件事：

**风险 1：`System/Item` 是全项目最脆弱的层。** 实体 Ca 均 36（`Player` 54、`Card` 42、`Item` 12；层均值 17.00 被数据类拉低）、A=0.00、**D=0.66**——被依赖最重却零抽象。含义：**最不该改的层同时最不可替换**。

**风险 2：`System/Rule` 抽象但不稳定。** A=1.00（全 `@abstract`）、I=0.59、D=0.59。抽象的收益被"仍被大量依赖"抵消；这类层的正确形态应是"高 A + 低 I"。

**风险 3：`System/Trigger` 与 `Global` 健康。** D 分别为 0.10 / 0.12，且 A 与 I 相称——只向外依赖、几乎不被依赖，符合它们的定位。

## 四、环依赖从哪来：类型声明，不是业务调用

v1.1 报「43% 类在环内」过于笼统。追查每条边后（工具 `_tool_arch_callgraph.py`），环的来源可归为四类机制，且**绝大部分不是业务调用**：

| 机制 | SCC 内边数（占比） | 例证 |
|---|---|---|
| 类型标注 | 143（52%） | `StageManager.handle_validated_request(request: OperationRequest, game_state: GameState)` |
| 常量/静态引用 | 73（26%） | `AreaManager.gd L11 const PUBLIC_PLAYER_ID = GameState.PUBLIC_PLAYER_ID` |
| 继承 extends | 39（14%） | `Stage`／`GameState` 等继承链 |
| 静态调用＋is 检查 | 15＋7 | `Class.method()`、`x is Class` |

**最小环 7 组**（互指对），典型两条：

- `AreaManager ↔ GameState`：前者为复用常量引用 `GameState.PUBLIC_PLAYER_ID`（L11），后者持有 `var area_registry: AreaManager = AreaManager.new()`（L18）。
- `BehaviorCommand ↔ GameState`（层间）：`CommandBus` 的**信号参数** `new_behavior(command: BehaviorCommand)` 与 `BehaviorCommand.execute(game_state: GameState)` 的**抽象方法签名**互指——这是命令总线设计的自然结果，不是耦合失控。

**三口径对照**（本轮类型声明网实测 43%、4 组环、涉及 83 文件；调用网与纯静态调用网为更早一次运行的值）：类型网 43% 环化、纯静态调用网 **0%**、补入实例方法调用后 **19%**。真实业务环只剩两组：

1. **命令-规则 29 类**：`RuleSettle` 会生成命令、命令又调规则，双向可追；
2. **渲染 4 元**：`RenderContext` 建 `RenderAreaManager`，`RenderArea` 反向持有 `render_context`。

**判读修正**：v1.1 的「类级依赖近乎一张网、隔离单元只能是层」应改为——**类型声明层确实是一张网（GDScript 强类型签名所致），但调用层接近 DAG**。可解耦的抓手是「减少签名里的具体类型依赖」（用基类／参数化），而不是「按层切分」；后者对类型网无效，对调用网的 19% 才有意义。

**层间 20 对双向依赖**同理：绝大多数由信号参数与抽象方法签名造成（如 `CommandBus` ↔ `BehaviorCommand`），并非层与层互相调用。


## 五、交叉验证：两把尺子指向同一事实

`RenderContext` 的 LCOM=349（内聚最差，全仓最高）与 0007 判定的"`@delegates` 转发层"是两条独立证据链：

- LCOM 用"方法是否共享成员"衡量；
- `@delegates` 用"副作用是否完全来自调用"衡量。

两者都指向"无状态转发器"。**含义**：单层打分易被自创口径带偏，跨层交叉验证才稳。

## 六、主张

**主张 1（层次不可混算）**：把 L1 的"分支数"和 L3 的"传播成本"放进同一百分制会得到不可解释的数。四层框架的第一纪律是**分层汇报、禁止跨层加总**。

**主张 2（范式台账覆盖标准框架没有的维度，反之亦然）**：12 维中范式台账贡献 1 维（设计意图），标准框架贡献其余 11 维中的 10 维（7 完整 3 部分）。两者是互补而非替代。

**主张 3（结构风险必须由结构指标发现）**：语义层读不出"`System/Item` 被 52 个类引用却零抽象"；Martin 的 D 能。单靠注解台账会漏掉结构性脆弱点。

**主张 4（本项目不是严格分层）**：43% 类在环内、20 对层间双向依赖、传播成本 0.31。见 §四。

**主张 5（交叉验证比单层打分可信）**：见 §五。当两把不同尺子指向同一事实时，结论才稳。

**主张 6（注解是标签，不是指标）**：Rule 层注解率 18.2% 而复用密度 72.1%；Manager 注解率 77.2% 而复用密度 27.5%——**排序几乎相反**。注解率测"声明密度"，复用密度测"可导出性"。

**主张 7（补贴注解不改变分数，只改变可审计性）**：v1.1 给静态方法补 77 处注解后，安全性/风险率/完整度**一个数都没变**（静态本就计入安全性分子）。收益是把"按前提视为原子业务"变成"已声明的原子业务"。

## 七、局限（结论封顶处）

1. **依赖图是上界近似**：类型标注也算依赖，故 43% 环化可能高估真实耦合。
2. **LCOM 高不等于坏**：无状态转发器天然高（`RenderContext` 349）。
3. **传播成本是静态可达性**，不是真实变更传播。
4. **未建立"指标—缺陷"相关性**：本文不声称任何指标低就一定有 bug，本项目也无缺陷基线数据。
5. 未采纳 MOOD 全套（EC/AC/POF）：需要"成员外部访问"与"多态调用点"计数，当前工具未实现。
