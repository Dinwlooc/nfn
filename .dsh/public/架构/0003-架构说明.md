# NFN 架构说明

keywords: 架构,三层,System,RenderControl,Transport,GlobalRegistry,插件层,扩展点,渲染路径,命令流水线

基线：2124597+WIP（2026-10-25）

**主层级三层各有中心**（系统 / 渲染 / 传输）；**副层级**是服务（插件）、注册表与配置表。渲染按"区域 → 单元 → 表现"逐级展开，系统侧由命令流水线 + 状态机修饰驱动，传输层以数据包与序列化路由收发，NPC 决策机独立在插件层。**本文只写结构与路径，不写具体数据。**

## 一、项目与场景

- 2D 多人环座回合制卡牌对战；引擎 Godot（mono，含 C# 互操作），渲染按"移动"方式驱动。
- 场景链：菜单场景（启动场景）→ 主游戏场景 `res://core/tscn/game/main_game.tscn`。场景根节点为 `Node2D`，内嵌面板类场景（如控制台）根节点为 `Control`。
- 全局单例：`GlobalConsole` / `GlobalTransport`（即 `Transport` 类本体）/ `GlobalConfig` / `GlobalTransition` / `GlobalRegistry`。
- **处理循环节奏**：主处理循环一律**帧计数门控**；长按一类的时间检测用**时间戳差**；不采用时间增量累加——后者要求连续的处理帧、不自动兼容离散时间切片，会限制方法的自由度（owner 裁定 2026-10-17，代价见 `0005`）。

## 二、主层级（三层，各自有中心）

| 层 | 中心 | 职责 |
|---|---|---|
| 系统层 | `System`（业务类中唯一直接继承 `Node` 的类；五个 `Global*` 单例另计） | 仅服务器端运行，执行业务逻辑与状态变更 |
| 渲染层 | `RenderControl` 及其子节点（多为 `Control` 派生） | 画面渲染与用户交互 |
| 传输层 | `Transport` | 服务器/客户端、逻辑/渲染层之间的通信枢纽：rpc 收发与正反序列化，并以信号向两层分发；连接生命周期与用户表在其 `NetworkManager`；增量顺序由数据包 `version` 承担，请求来源合法性在系统层操作处理器验证 |

## 三、副层级

- **服务层（插件层，`Other/`）**：控制台、计时器、转场等孤立节点，提供轻量功能与轻量通信——计时器一类服务端节点可经 rpc 直接与客户端同路径节点通信，**不经过传输层**。插件挂在这一层，当前有 NPC 决策 Agent（`Other/Agent`）。转场（`GlobalTransition`）提供带保护的场景切换（淡入淡出）。
- **注册表**：`GlobalRegistry`，两类实际职能——常量名↔索引双向映射（数据包序列化在用），以及单例注入/按需连接（控制台、计时器、渲染根等）。**渲染区域与渲染单元的注册不走这里**，那部分在 `RenderContext` 的管理器里。
- **配置表**：`GlobalConfig`，动态资源的加载与获取入口，从资源包（官方包 + mods）的配置文件读取键与路径。

## 四、渲染层（实测）

- **根**：`RenderControl` —— 接住传输层的渲染请求并节流处理，托管上下文、Face 层与操作管理器，并挂控制台指令入口。
- **上下文**：`RenderContext` —— 聚合「区域 / 卡牌 / 状态 / 操作」四个管理器，作为 Face 层与根的统一入口；**自身不持有渲染数据**，只做转发与跨管理器协调。区域 / 卡牌 / 状态三个管理器由上下文自建，操作管理器由根创建后注入。
- **区域**：`RenderArea`（抽象基类）→ 列表型 `ItemRenderArea`（持卡牌 + 树索引）/ 计数型 `ItemCounterArea`。具体区域按**静态区域名注册进工厂**并由 `RenderAreaFactory` 创建；场景内区域由根在就绪时注册进上下文（动态创建的经管理器创建信号由根接管初始化），退出时自注销。
  - 当前工厂已登记 6 类：`hand` / `defence` / `center` / `discard` / `drawing` / `ability`。
- **单元**：`RenderItem` 是通用"渲染单元"——存卡牌数据即卡牌、存玩家数据即玩家，**它本身不需要扩展**，扩展点在其承载的数据包与渲染事件。
- **表现**：Face 层（`AreaFace` / `ItemFace`）由**编辑器场景**实例化，通常作为区域或渲染单元的子节点；Face 管理器按数据从配置表取场景部署，走对象池。
  - 区域作为渲染单元子节点时，Face **不会自动加载**，由该单元的 Face 负责。
  - 需要访问其他区域时一律经上下文，不互相持有。
- **事件与请求路径**：`RenderEvent` 以字典携带渲染/补间参数；请求自传输层进入根队列 → 目标区域 → 单元 → 表现，逐级以信号下发。
- **三个管理器的分工**：区域的生命周期与回调替换、卡牌池与映射、拖拽与阶段状态，分别独立管理。

## 五、系统层

- **数据管理器**（`GameState` 的属性，**不反向引用** GameState）：卡牌 / 玩家 / 区域 / 阶段 四个管理器。
- **顶层模块**（`System` 的属性，**可持有** GameState 引用）：`command_processor` / `command_bus` / `operation_handler` / `trigger_manager` / `modifier_manager` / `transport`（另持 `GameTimer` 引用）。NPC 一侧不在 `System` 属性里：系统侧只有 `System/Trigger/AgentTrigger` 做接线，决策机本体在插件层 `Other/Agent`。
- **NPC 决策**：决策机在插件层（`Other/Agent`），接口只有两件事——输入快照、输出操作请求；系统层与渲染层各自的 NPC 管理器只负责快照取数与请求转发。快照为纯数据，决策不接触游戏状态或渲染上下文。渲染端 AI 托管复用同一 Agent 与同一决策机。
- **命令流水线**：操作请求 → 阶段创建行为命令 → 经阶段管理器补全、转发、入栈 → 命令处理器每次被调用只推进**栈尾命令的一个阶段**；这段接线的桥接与时机由触发器部署——命令压入/弹出时维护 `GameState` 的命令上下文栈，每次推进前把命令上下文交给修饰管理器，**状态机每一步都是修饰时机**。
- **行为命令**：后进先出栈；自身状态机的"取消 / 完成"标记互相独立；可创建并关联并发命令，实现连锁与复合行为；每类定义自己的上下文内部类，并沿继承链扩展。
- **阶段**：主阶段为固定顺序的循环序列，临时阶段以栈保管；静态规则工具类被阶段复用，采用**验证器字典**按卡牌类型分派，并接受卡牌级验证覆盖，使具体卡牌可开关规则。
- **修饰**：修饰管理器按「主修饰卡牌 → 主修饰玩家 → 其他在座玩家（自当前回合玩家起按座位轮询，每个对象仅一次）」顺序执行，可改参数或追加命令；数值修饰走属性修饰器（玩家与卡牌的属性），必要时合成为临时修饰器。
- **触发器**：为系统或状态部署信号回调，或基于数据变更与游戏状态追加命令。
- **命令总线**：各业务类发送命令入栈的统一入口，命令相关信号已从 `GameState` 移驻于此。
- **缓存约定**：卡牌与玩家各自缓存其数据包；取包时默认返回**相对缓存的增量包**并更新缓存，或返回当前缓存的全量包。

## 六、传输层

- `Transport` 用 rpc 收发 `TransPack`：**系统层 → 渲染层**发渲染请求；**渲染层 → 系统层**发操作请求（经操作处理器验证后交阶段管理器，接线由触发器部署）。连接生命周期、对等体与用户表由 `NetworkManager`（WebSocket）承担。
- **三大数据包族**：物品包 / 渲染请求 / 操作请求，各自配有对应序列化路由。物品操作请求已收敛为单一 `ItemsOperation`：枚举区分官方操作（枚举 0 为自定义模式，另带名称），统一参数面为「源区域 / 源 ids / 目标区域 / 目标 ids」，字段按操作类型的标准态物化；分派键由 `get_operation_name()` 承担。通用放弃请求仍是独立类型 `AbandonResponse`（详见 `0023`）。
- **序列化**：数据包子类自实现正反序列化与重建；工具类提供项目自定义流式读写；序列化器系列以**脚本类映射表**做路由——**新类型只追加，不插队**（下标即线上标识）。

## 七、扩展点（写新功能时改哪里）

- 系统层：卡牌、区域、阶段、命令、规则（静态工具类）。
- 插件层：`Other/Agent`（决策机；新增能力仍守"快照进、请求出"）。
- 传输层：三大数据包子类及其序列化器（`ItemSerializer` / `RenderRequestSerializer` / `OperationRequestSerializer`）。
- 渲染层：**`RenderArea`**（新增区域类型，并在 `RenderAreaFactory.area_classes` 登记）；`RenderItem` 不需扩展；渲染参数用 `RenderEvent` 的字典扩展——建议每个扩展用**自定义常量类**做键，便于他人查阅。
- 资源与表现：卡牌资源类；`ItemFace` / `AreaFace` 作为子场景根节点随场景实例化。

## 八、与 owner 设计文档的差异（实测修正）

- 文档提到"`RenderManager` 接收区域信号后把渲染单元加载进场景树"——当前代码中**没有 `RenderManager`**：列表型区域自己管理池与树索引，表现层由 Face 管理器部署、渲染参数由渲染事件承载。本文按当前代码书写。
