# 0005 帧处理循环与用户体验

keywords: 帧循环,节流,帧控制,时间增量,UX,队列,owner裁定

**摘要**：项目的帧处理循环（帧计数取模节流 + 队列摊销 + 空载停机）在参考帧率下紧凑、匀速、可预测。v1.1 曾把"节奏随帧率双向失真"判为缺陷并首选时间基准改造；2026-10-17 owner 裁定：**主处理循环一概采用帧控制**——帧耦合是刻意设计，失真代价被接受；时间增量算法因限制方法自由度（要求连续处理帧、不自动兼容离散时间切片）不采用，长按类时间检测用时间戳差值。v2.0 保留 UX 代价的完整记录（含对裁定理由的一条代码级佐证），优化意见收缩为与帧控制兼容的项：吞吐诊断 → 队列预算排空 →（可选）帧基准节拍服务，另登记一处与裁定对齐的转换候选。

- v2.1 ｜ 2026-10-26 ｜ glm-5.3-flash ｜ 0004 清理后的引用标注：快照行加"数字失去复跑来源"声明；正文各处 `0004 v2.0` 引用所指数据自此为孤证，重测前不得当可复核依据。（依 README 交叉编修规则升小数位）

## 一、框架现状（代码亲验）

三个业务循环共用同一模式——`_process` 内以 `Engine.get_process_frames() % N` 取模门控，命中才做一小步：

| 循环 | 门控 | 参考帧率（60fps）下 |
|---|---|---|
| `RenderControl._process` | `% 10` → 请求队列出队一件 | 6 件/秒 |
| `System._process` | `% 4` → 命令栈推进一阶 | 15 阶/秒 |
| `Transport._process` | `% POLL_FRAME_INTERVAL`（=6）→ 网络轮询 | 10 次/秒 |

配套件：渲染请求 FIFO 队列（每拍一件）；命令栈空时经触发器关停 `System` 的 `_process`（空载零成本）；补间与计时（Tween、GameTimer）为时间基准，与上述帧基准并存。三组节拍数（6/15/10 每秒）形似以 Hz 为意图的取整——该解读已由 owner 裁定回答：**帧控制为刻意设计**（见第三节）。

## 二、优点（用户体验视角）

1. **切片摊销，不雪崩。** 突发负载被切成"每拍一件"，不会堆进单帧造成长帧——0004 v2.0 实测插电 60fps 下 p50 帧间隔 16.67ms、p99 17.82ms，分布极紧。用户得到的是"匀速排空"，不是"卡一下再爆快"。
2. **降级形态体面。** 超载时表现为整体变慢但连贯（owner 对电池态症状的描述即如此）——对回合制卡牌，这优于掉帧、撕裂或冻结；队列天然背压，越忙不会越乱。
3. **空载自适应停机。** 无命令时系统层循环整段停摆——对挂着等对手的对局是真实的电池友好。
4. **节奏确定、可测。** 固定帧率下节拍完全确定，回归测试可按帧断言；渲染层实测的可复现性即建立在此上。
5. **方法自由度（owner 裁定的核心理由，v2.0 补）。** 帧计数把每个处理机会当成无状态的离散事件：循环可随时停摆、恢复、跳帧而不需要补偿逻辑；时间增量累加器则要求连续的处理帧，遇离散时间切片要么吞下大增量、要么补写补偿逻辑。这是 v1.0 低估的一侧（佐证见第三节末）。

## 三、裁定与已接受的代价

**owner 裁定（2026-10-17，原话）**："对于主处理循环，一概采用帧控制。对于长按时间检测等，则使用时间戳差值判断。时间增量算法会对方法的自由度进行限制，即要求连续的处理帧，不自动兼容离散的时间切片，所以一般不采用。"

以下各条因此从 v1.1 的"缺陷"改判为**已接受的取舍**，记录保留——它们是帧控制的真实后果，未来任何人动这些循环都该知道自己在动什么：

1. **节奏的单位是帧，感知的单位是时间。** 0004 v2.0 §三已证一半：外部把 60fps 砍到 30，三循环吞吐同时减半，出牌反馈与转场耗时翻倍。反向同样成立（推理级）：高刷屏或关 vsync 时节奏**加速**——实测插电关 vsync 达 599fps，此时命令推进约 150 阶/秒，游戏"赶拍"。耦合是双向的。
2. **平台风险。** 项目以 Mobile 渲染器为目标档：移动端 30fps 省电、录屏、远程桌面、驱动限帧（0004 v2.0 定案的 Battery Boost 即一例）都会改帧率，任何一种都直接改手感——自此为已接受行为。
3. **多人公平性（推理级）。** 系统层仅服务器端运行，节奏跑在主机帧循环上——主机被限帧，**所有客户端**一起变慢。
4. **无界积压，无追赶。** FIFO 每拍只出一件、无截止时间：30fps 下一次多发牌的可见完成时间成倍增长。通用 UX 经验：反馈延迟百毫秒级开始可感，两三百毫秒以上明确感知为迟滞（行业常识转述）。（可兼容的缓解见四之 P2。）
5. **三循环同拍撞击（推理级，待测）。** 模数 4/6/10 的最小公倍数为 60：每 60 帧三循环同帧触发（60fps 下每秒一次）。（可选处置见四之 P3。）

**裁定理由的代码级佐证**：0004 v2.0 §四实测"窗口失焦会冻结/降频主循环"——这正是"离散的时间切片"的活例：帧计数在恢复后干净续跑，时间增量累加器则要面对失焦期间积累的墙钟时间；`System` 循环经触发器 `set_process` 整体停摆/恢复，同理。

## 四、优化意见（收缩为与帧控制兼容的项；全部需授权，未改代码）

1. **P4 · 吞吐诊断指令（成本最低，建议先落地；与帧控制完全兼容）。** 借现有控制台基建加一条指令，暴露请求队列深度与三循环有效吞吐——代价既被接受，至少让它可观测：节奏回归从体感变成可断言的数字。
2. **P1 · 时间累加器替换取模——已作废（v2.0）。** owner 裁定主处理循环一概帧控制、时间增量不采用（理由原文见三）。存目仅为避免后人重提。
3. **P2 · 队列预算排空（保持帧控制的改造）。** 帧门控不变，仅命中时在预算内连续出队（设上限）：有余量时突发快速消散，无余量时优雅降级。注意"每拍一件"本身是否刻意设计**未经裁定**——落地前需 owner 单独确认。
4. **P3 · 帧基准节拍服务（可选，架构级，需裁决）。** 服务层加节拍器孤立节点，集中声明各循环门控模数并错峰触发（仍为帧控制），顺带处置三之 5 的同拍撞击待测项；为慢放/回放/调试留单点。
5. **对齐候选 · 长按检测转时间戳差值。** `RenderItem.request_dragging` 现为 `await get_tree().create_timer(0.1)`——既非帧控制、也非裁定要求的时间戳差值（await 挂起方法，与"方法自由度"的理由相悖）。按裁定应转换。需授权。
6. **外部侧（解耦既已否决，这是节奏失真的唯一缓解）。** 电池态 30fps 锁按 0004 v2.0 §二待确认动作处理（驱动开关）；帧率变化下的节奏变化自此为已接受行为，不再作为游戏侧缺陷追修。

## 适用范围

UX 代价记录适用于本项目及同类帧数量化节流项目。**时间解耦类改造（原 P1）对本项目不适用**——owner 已裁定主循环刻意帧锁定，本项目正属 v1.0 所写"不适用反例"之列。四之 5 的转换候选适用于全项目所有时间检测处。

## 复核方式

- 代码主张：`grep -rn "get_process_frames" core/` 应得三处门控（RenderControl / System / Transport）；长按现状：`RenderItem.gd` 内 `create_timer(0.1)`。
- 耦合的文档化证明：同一操作序列（如 `c_start` 后 `c_draw`）在插电 vsync 与插电关 vsync 两种状态下各测"指令到卡牌入手的墙钟时间"——两者应显著不同；此测试自 v2.0 起证明的是**已接受属性**，不再是待修缺陷的基线。
- 推翻路径：P2/P3 若被 owner 否决 → 四中存目；长按转换完成 → 四之 5 改为既成事实；双机实测主机限帧不影响客户端节奏 → 三之 3 作废；实测同拍撞击不可见 → 三之 5 降级为无影响。
