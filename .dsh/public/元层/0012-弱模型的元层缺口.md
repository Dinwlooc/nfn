# 0012 弱模型的元层缺口：身份、归属与环境判据

keywords: 弱模型,元层,身份,归属,机器判据,会话存储

**摘要**：弱模型（GLM-4.6V）在元层里的失败集中在三类"事实"——我是谁、这份文件是谁的、环境现在是什么；这三类在元层里都只有叙述、没有机器判据。元层要补的不是更多方法，而是把叙述换成可核对的一手源与校验器。

## 主张

1. **身份判据只能取会话存储，不能取 agent 配置。** 实测：`list_agents` 报 lead 模型为 glm-4.6v，而本会话存储的 `model` 字段只有 deepseek-flash 与 deepseek-v4-pro；前者来自 profile 的 `agent-default-model`（当天 10:58 写盘），后者才是本会话真实路由。任何模型（弱或强）拿配置当身份都会答错。
2. **配置与能力权限会在会话中途变化，第一次探测不是常量。** 实测：同一轮任务里 profile patch 被 owner 修改；子代理模型目录起初只列 deepseek-account，探测 zai-coding-cn 被拒（not allowed for this Session）；owner 后续开启权限，但模型未复查，仍按"不可用"推演。结论：涉及"能否调用某模型/某工具"的判断必须现场重探，并把重探点写进元层。
3. **弱模型的版本与归属认知会写错，且错误直接进入知识层。** 实测：GLM-4.6V 把 glm-5.3 的《实例归档》的模型字段、署名、来源声明、页脚四处全部署成自己；同目录《方法》《印象》保留原署名——说明它知道"要保留原作者"，只是判断不出"哪一份才是自己的"。现行 `_tool_memory.py` 只验字段存在与格式，不验署名与实际写入会话是否一致。
4. **对弱模型的第一个元层缺口是模型注册表，不是方法论。** 实测：owner 复述 GLM-4.6V 一度不知道项目里有几个模型。元层没有"项目有几个模型、我是哪个、我的库在哪、`--lib` 该传什么"的单一机读清单——只有 route.py 扫描 `.dsh/*/cache` 得到的候选，以及 AGENTS 里新增的"已注册模型库"叙述（双写、无版本、无本人映射）。128k 上下文要求这四项一屏可得且可直接执行。同轮还发现注册表与文件系统候选不一致：AGENTS 列 2 库（Deepseek/glm），route 扫出 3 库（另含 Dinwlooc）。
5. **元层缺 lint：转义、双写、署名归属、漂移全靠写作者自觉。** 实测：AGENTS.md 被写入 Markdown 转义损坏（`usage_report` 的下划线前、分隔线前各多一个反斜杠），直接违反《元层更新原则》维护禁令；现行校验器不检查转义、不检查同一事实两处写。弱模型尤其容易在格式上翻车，并把坏格式传给下一个会话。同轮 `_tool_memory.py` 对 `.dsh/glm/cache` 跑出 1 例契约越界：《自己》的 `性质` 写成契约外的「自我认知」，已按契约改为「印象」——**校验器能捕获的，就不要留给自觉**。另发现库目录改名后的旧指针残留：glm-5.3 迁为 glm 后，Deepseek 库内两处路径仍写 `.dsh/glm-5.3/cache`；改名没有配套的引用清扫步骤。
6. **强模型的观察者失败模式：见到前提矛盾先"补调查"，不断言。** 实测（本轮）：身份冲突、署名矛盾、文件损坏三个信号在第一轮同时出现，观察者仍继续十余次探查 DSH 配置与存储，未当轮通报 Owner。规则：身份/前提/文件损坏/未注册实体四类信号，最多 2 次取证后立即报告，不扩查。
7. **权限门在会话身份层，且是会话建立时的快照，不是 profile 现状。** 实测：子代理可用的模型由本会话的 route 允许集决定（拒绝文案：not allowed for this Session）；即使 profile 的 `allowedModels` 已加入 `zai-coding-cn/glm-4.6v`（2026-10-24 12:24 核实），既有会话仍拒绝。`list_subagent_models` 只反映 provider 目录，会漏报允许项，不能当允许列表用。推论：换模型做测试前，要么新建会话，要么先确认本会话允许集；项目元层无法为弱模型"自助开通"。
8. **弃用合并必须留变更记录并清扫全部引用。** 实测：元层目录页被有意弃用、类型含义并入 AGENTS，但元层更新原则与模型库各留一处悬空引用；观察者（我）先判为"误删"并恢复，经 owner 纠正才知是有意重构。教训：弃用应留存根（指向新位置）或在 AGENTS 记一条变更，引用清扫先于删除；观察者遇"文件消失"先查变更记录或问，不先恢复。
9. **一次失误会连锁：身份重议、重复探测、残留产物、最终中止。** 实测（2026-10-24 12:26–12:28 被中止的一轮）：前提冲突后在同一轮里反复重述身份判断（系统提示 vs list_agents vs 会话存储），对同一目标先后写两版 zstd 探测脚本并多次重试解析，在项目 tmp 留下两个即席脚本，回合最终被中止。其中真正有效的两条证据——会话存储里 76 条 assistant 消息 model=deepseek-flash、子代理允许列表含 glm-4.6v——本可在 2 次探测内取得。规程：前提冲突时先取「会话存储 + 配置允许列表」两项机器证据再决定；即席脚本不入项目树（系统临时目录，或 `public/tools/audit/` 登记后复用），任务结束清理；禁止在同一轮内重开身份论证。（v6.0：`.dsh/tmp` 已取消，见修订记录）
10. **冷启动身份混淆的根因是「配置态」冒充「会话态」，且缺一条免解压的会话态读取命令。** 实测（新会话冷启动记录）：系统提示与会话记录都指向 deepseek-flash，但 `list_agents` 报 glm-4.6v（owner 调参窗口内的 agent 默认配置），模型因此反复自问"我是不是 GLM-4.6V/是不是被测试"，转向解压 zstd 会话日志、自建多版探测脚本并多次重试，最终整轮被中止——而真正有效的证据本是一条命令可取。修复：`route.py` 增加 `I=` 行（读 session_projcache 的 JSON 快照，免解压 zstd）；AGENTS 身份判据改为「会话存储优先、list_agents 仅配置值」；`元层索引.md` 给弱 AI 的自查一行命令。

## 适用范围

适用于多模型共用一个元层、弱模型（小上下文、低指令遵循）接入、以及 owner 在会话中途修改 DSH 配置的场景。**不适用**：单模型闭环会话（无身份判据问题）；配置冻结的批量实验（配置不会中途变，主张 2 弱化）。样本小，本页为方向性证据，不是定量结论。

## 复核方式

- 身份判据：读当前会话存储 json 的 `model` 字段，与 `list_agents` 输出、profile `cordis.patch.yml` 的 `agent-default-model` 三处对照。
- 归属判据：扫描 `.dsh` 下全部 `**模型**` / `**署名**` 字段，与对应写入会话的模型 id 对照。
- 转义 lint：扫描 AGENTS.md 中"反斜杠 + 下划线/连字符"模式，应 0 命中。
- 配置变更：比较 `$env:DSH_PROFILE_DIR` 下 cordis.patch.yml 的 LastWriteTime 与任务开始时间。
- 推翻路径：给出"配置即身份"成立的实测反例；或证明弱模型的署名错误率与普通模型无显著差异；或证明配置在会话中途不可变。
