# 0024 记忆库插件能否升级元层知识库（2026-10-27）

keywords: 记忆插件,mneme,memsearch,mnemon,engramory,知识库,签发制,第二真相源

**摘要**：逐条拆了四个记忆库插件的 README、tarball 与依赖图，结论是**它们都不能升级本项目的元层知识库**——知识库是"可审计、按任务路由、签发制"的契约库，插件给的是"自动写入、模糊召回"的情节记忆；混用时最大风险是出现第二个无签名的真相源。可借的是三个机制（索引硬上限、冲突冻结、候选审核），不是一个包。证据来自 npm packument / README / tarball 源码结构与 GitHub 元数据，**未实装运行**。

## 0. 结论

1. **不能替换**：`@modusensus/dsh-mneme`、`@zilliz/memsearch-dsh`、`dsh-mnemon`、`dsh-engramory` 的召回对象都是**自己新建的记忆库**，不是 `.dsh/**/*.md` 正文。mneme 的 `document` 类型只存"摘要 + doc_path"，正文仍留在磁盘由 agent 自管——**对现有 104 篇论文没有语义检索能力**。
2. **最大风险是第二真相源**：记忆条目没有 sha8、没有 revisionBasis、没有 active/superseded 状态机；一旦自动注入的"教训"与某篇签发过的论文冲突，模型无法用现有判据裁决谁对。这直接违反 META 策略的"契约要可证伪"。
3. **成本结构与缓存纪律冲突**：mneme 注册 **11 个模型工具**（`memory_save/search/list/get/update/delete/forget/archive/register_document/organize/runtime`），且 `autoSummarize`/`autoDream`/`autoInject` 默认全开（`turn/end` 摘要、记忆 >10 条时后台 LLM 巩固、开局注入）；memsearch 每轮注入 reminder、每轮摘要，还要 Python + `uv tool install memsearch[onnx]` + Milvus。
4. **最契合的其实只有机制**：engramory 用 `ctx.tools.guard()` 把索引硬限制在 200 行 / 25 KB（超限的**增长写入被拒**），这与我们"必读清单每次会话都要加载"的约束同构，但它**不提供检索**。
5. **建议**：不装；把三个机制借进知识库（§4），需要情节记忆时再单独上 mneme 且关掉自动三件。

## 2. 为什么"不能当升级"（三条硬判据）

1. **对象不同**：知识库的条目是判据、口径、协议与事故；记忆插件的条目是偏好、历史、摘要。前者要求"精确命中 + 可引用行号"，后者追求"相关即可"。把判据塞进记忆库，等于放弃按任务路由（`meta_route` 的必读清单是**契约**，不是检索结果）。
2. **写入权不同**：知识库写入 = 原生 write/edit + `meta_sign` 签发（sha8 可审计、revisionBasis 可追责、状态可墓碑）。记忆库写入 = 模型自己调 `memory_save` 或 turn/end 自动摘要，**没有第二人复核**。两种写入权混在一个库里，审计链会断。
3. **规模与形状不同**：当前库 104 篇 / 5,401 行 / 27.8 万字符（≈7 万 token），单次任务必读 15 篇（实测 408 行 / 22.6k 字符）。记忆插件面向"几百条短条目"，其注入策略（只注入 summary + 高重要度 5 条）在契约场景下会**漏掉必读**。

## 3. 成本账（按本项目口径）

- mneme：11 个工具若常驻，schema 粗估 ~2k token/请求；走 `tool-search` deferred 可省，但**每次调用注入会打断前缀缓存**（0015：一次断裂中位 37.6k token）。自动三件默认开：turn/end 摘要（每会话一次 LLM）、autoDream（>10 条记忆时后台 LLM 巩固，官方文档承认撞顶会重跑）、开局注入（每会话固定 token）。
- memsearch：每轮 reminder（小）+ 每轮摘要（LLM）+ 首次建索引（本地 ONNX）+ Milvus 进程。跨工具共享（Claude Code / Codex / OpenCode）是本项目**用不上**的能力。
- 在当前 ¥5 量级的任务预算下，这两者的"固定开销 + 后台调用"会挤掉真正的工作 token。

## 4. 可借的三个机制（不装包也能做）

1. **索引硬上限**（来自 engramory）：给必读清单加一条上限（行数/字符），超限即拒绝增长、只允许压缩。理由与我们相同：必读每次会话都加载，超出的部分会**静默不生效**。当前 15 个必读文件合计 408 行 / 22.6k 字符，单篇最大 170 行；engramory 的 200 行是**单文件**档位，我们的约束应按"每次任务加载总量"定档（例如 600 行）。
2. **冲突冻结**（来自 mneme `conflictFreeze`）：论文之间的冲突不自动裁决，冻结进队列人工/复核者选边。我们目前只有 `state: superseded/refuted` 单条字段，没有"两条互相矛盾"的显式建模。
3. **候选审核**（来自 memsearch `memory-to-skill`）：自动产出的"经验"只进候选区，**安装/生效是人的一步**。这与我们的签发制同构，可作为"自动整理论文"的护栏。
