# 0026 空 tool-call id 锁死会话与探索行为治理（2026-10-27）

keywords: 空id,toolCallId,session-repair,loop-guard,探索熔断,被动约束,repeat-tool-reminder,会话修复

**摘要**：按 Owner 转来的故障报告逐条核了源码：适配层 `dsh-llm-pi-ai` 把 provider 的空 id 原样写进 tool-call block（无兜底），空的 `toolCallId` 在 `dsh-session-format-v3-to-v4` 的校验里被判非法，且报错文案把"为空"说成"不匹配"。处置上不写新的"清理插件"：历史修复交给 `dsh-session-repair`（覆盖空 id 链三形态、强制备份、可回滚），推理空转交给 `dsh-loop-guard`，工具重复试错交给自研 `nfm-exploration-guard`（同步否决，被动优先）。三者分层：存储恢复 / 流熔断 / 调用否决。

## 0. 结论

1. **报告方向正确，两处需修正**：校验点在 `dsh-session-format-v3-to-v4`（不是 `dsh-session` 本身）；适配层根本**没有** `?? 'call-N'` 兜底，只有 `toolcall_delta` 分支的 `known?.id ?? ""`，`toolcall_end` 直接 `brandString(event.toolCall.id)`。
2. **不新写"清理非法内容"插件**：已存在专门件 `dsh-session-repair@0.7.0`，它把"空 tool-call ID 链"列为确定性可修问题（字段缺失 / `null` / `""` 三形态，整链修 `assistant/message` + `tool/call` + `tool/result`），并强制 pre-repair 备份、留审计、可一键回滚。上游 discussion #4365 已把它的 closeBlock 兜底采纳为引擎侧修复蓝图（写入侧根治，插件是读取侧恢复）。
3. **`dsh-messages-sanitizer` 不是同一层**：它治的是 OpenAI 协议配对违规（孤儿 `tool_calls` → 400 INVALID_REQUEST），我们的故障是本地 `SessionFormatError`（写盘校验失败），装它不解决。
4. **探索行为分两种，工具不同**：只想不做的推理循环用 `@mrweicodes/dsh-loop-guard`（在 `llm/stream` 内部切断，回合正常收尾）；参数不变的重复试错用自研 `nfm-exploration-guard`（`ctx.tools.guard` 同步否决）。内置 `repeat-tool-reminder` 只是**提醒**（3/5/8 次），不拦。
5. **不塞进 meta-tools**：meta-tools 管提示词库的路由与签发，不碰会话持久化与工具流水线；混在一起会让"知识层"与"运行时防护"耦合，回滚粒度也会一起烂掉。

## 1. 故障链核实（源码级）

| 环节 | 包 | 事实 |
|---|---|---|
| 适配 | `dsh-llm-pi-ai/lib/index.js` | `case "toolcall_end": ... block: { type: "tool-call", id: brandString(event.toolCall.id), name: event.toolCall.name, ... }`——空 id 原样透传，无 `call-N` 兜底 |
| 失败 | `unknown tool ""` | 空 name 导致工具解析失败，抛 `ToolNotFoundError`（报告所见文案） |
| 写盘校验 | `dsh-session-format-v3-to-v4/lib/index.js` | `if (typeof toolCallId !== "string" || toolCallId.length === 0 || sourceCallId !== toolCallId) throw new SessionFormatError(... "requires toolCallId matching its tool source")`——**空与不匹配共用一条文案**，所以按"id 是否匹配"扫描找不到违例 |
| 锁死机制 | agent loop | 失败结果写不进去；`assistant/message` 已提交，恢复时重新发现"待执行调用"，同一步再次失败 → 永久卡住；日志尾部干净，所以扫描看不到坏行 |

**报告里"校验在 dsh-session"需改写为 `dsh-session-format-v3-to-v4`**；其余因果链与"文案误导"判断成立。

## 2. 处置：三件工具分层

| 层 | 工具 | 作用 | 状态 |
|---|---|---|---|
| 存储恢复 | `dsh-session-repair@0.7.0` | 诊断（只读 `dsh_session_repair` 工具）+ 面板「备份并修复」；覆盖空 id 链三形态；pre-repair 备份、审计、一键回滚；live/歧义/文件变化一律不写 | **已装**（applied） |
| 推理熔断 | `@mrweicodes/dsh-loop-guard@1.0.10` | `llm/stream` 瀑布内切断"纯推理空转/复述材料/周期循环/短语池重排"；默认 `escalate: steer`（只结束本次调用）、`resumeAfterBreak: false` | **已卸载**（2026-10-28 Owner 判定：边界防御未防住，26 次切断未止住推理死锁） |
| 调用否决 | `nfm-exploration-guard@0.1.0`（自研） | 同一 agent 上"工具名 + 参数 sha1"连续相同 > 6 次 → 第 7 次起同步否决，理由回给模型；参数一变即重置；轮询工具豁免；异常一律放行 | **已装**（applied），6/6 夹具 |

## 3. 为什么是这三个，不是"一个万能清理插件"

1. **职责分属不同子系统**：写盘校验在 session format 层，流式生成在 llm 层，工具调度在 tools 层。一个插件同时碰三层，任何一层的 bug 都会让另外两层陪葬，且无法单独回滚。
2. **历史与未来要分开治**：已被写坏的会话只能读侧修复（改历史有风险，所以 session-repair 坚持备份 + 指纹 + 原子替换）；未来的坏写入应在引擎层兜底（上游已采纳）。运行时插件再做一次"否决"只对**可判定的**形态有意义（重复调用），对"空 id"这种协议级缺陷不应重复实现。
3. **被动优先的排序**：否决（无需模型配合）> 切断（无需模型配合）> 提醒（需要模型配合）> 事后审计。本轮的组合把前两档铺满：
   - 推理空转 → loop-guard 切断（被动）
   - 参数不变的重复 → exploration-guard 否决（被动）
   - 工具链重复 → 内置 `repeat-tool-reminder` 提醒（主动，未改）
   - 变更churn → `@raphelutumn/dsh-change-budget`（**未装**，0★，仅改文件类工具，留观）

## 4. exploration-guard 判据与边界

- 判据：`工具名 + 参数 JSON 的 sha1` 连续相同计数 > `maxIdentical`（默认 6）。按 agent 用 `WeakMap` 隔离；豁免 `job_output` / `job_list` / `job_kill` / `job_wait` / `mcp__godot-ai__logs_read`。
- 否决是**单调**的：`ctx.tools.guard()` 返回理由即拒，任何后续监听器翻不回来；计数不清零，模型不换方法就一直被拒。
- 不拦"不同参数的穷举"——那是真探索，代价该由预算纪律管（budget-watch + OL1H），不是守卫管。
- 不碰 `llm/stream`、不改参数、不注入消息、不写会话事件。
